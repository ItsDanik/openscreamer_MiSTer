# OpenScreamer hybrid core for MiSTer (Screamer, Screamer 2)

@hybrid/CLAUDE.md

## This core

- Name everywhere: `OpenScreamer` (the engine: core, folders `games/dnk/OpenScreamer/` and `logs/dnk/OpenScreamer/`, `_Other/dnk/dnk-OpenScreamer_*.rbf`, release), `openscreamer` (game submodule, binary in `build/`, log, lock). The games and their menu entries (`_Other/dnk-<title>.mgl`): `package/games.txt` (`S1|Screamer`, `S2|Screamer 2`, set names `OpenScreamer_S1` / `_S2`), the same as in the catalogue of `hybrid/launcher/danik_hybrid_ports.sh`.
- The game is the `openscreamer/` submodule, branch `mister`. Its MiSTer code is behind the `MISTER_HYBRID` build option.
- Build: `./build.sh` (game), `./core/build_core.sh` (FPGA), `./package.sh` (zip in `dist/`), `MISTER=root@<address> tools/deploy.sh`.
- Try a build on the MiSTer without installing it: `MISTER=root@<address> tools/test_on_mister.sh S1|S2|list|nodata|log|stop` (the rule in `hybrid/CLAUDE.md`). `TEST_ENV="OS_TALL=1 OS_WIDE=1 OS_LOCK30=1"` fixes the size (either switch stops the OSD's being followed: `OS_WIDE` alone once made the menu start again for ever, the OSD saying 320).
- Lines marked `GAME:` in the scripts and `TODO` in the READMEs are the places the template left for this game.

## This game

- The game's own repository is `~/openscreamer` (`ItsDanik/openscreamer`, branch `main`, the PC version; its `CLAUDE.md` is the long record of the reverse engineering, `docs/NOTES2.md` Screamer 2's). The submodule here is its branch `mister`, kept equal to `main` (fast-forward the other after work on either). MiSTer code: `port/src/mister.[ch]` and lines inside `#ifdef MISTER_HYBRID` (search for `MISTER:`).
- The games' data goes in `games/dnk/OpenScreamer/screamer/` (Screamer: DATA, GFX, CONFIG) and `.../screamer2/` (Screamer 2: DATA, GFX, ANIMS, CONFIG, music/track_NN.ogg), settings and saves of both in `.../saves/` (Screamer 2's files are `openscreamer.s2*`). The first release had Screamer's folders straight in the game's folder: still taken when `screamer/` has not got them. Never in a repository or a zip. The READMEs say to copy each game's folder whole (Danik, 2026-10-18: they had said which files could go, and a player who took out one too many had black menus). `game_check` (`port.c`) looks for every container Screamer 2 opens, `ANIMS` and the menus' `GFX` ones included (those only looked for, not read through: reading them took 2.6 s more from the SD card); the core's message names the missing ones whole, "and N more" for the rest (`name_add`).
- **Which game** (`mister_pick_game()` in `mister.c`, from `os_init()` in `port.c`): `MH_PickGame()` with each game's files (the ones `game_check()` asks for), the set name from the menu entry, else the core's list of those found; then `-data screamer|screamer2|.` and `-game 1|2` as the PC has them. There is no first page choosing the game on the MiSTer (`PAGE_GAME`: `K->both` is never set with `-data`). Picked from the list, the game leaves with 42 (`OS_MISTER_LISTED` in the environment, which outlives the port's parts). Damaged or missing files after that: `game_check()` puts the list on the core's picture (`mister_fatal()`). The messages are in `mister.c`.
- Static SDL and the port's "parts": the port puts its own statics back between menu, race and intro. `port/CMakeLists.txt` joins the game's objects into one and renames their `.data` / `.data.rel*` / `.bss` to `osdata` / `osbss`; `port.c` saves only those. A new writable section in the objects (see `readelf -S`) must be added to that list.
- Time is the core's fields: `SDL_GetTicks()` is `mister_ticks()` in the game (`port.h`), and a picture is shown once a field (`SDL_MISTER_VSYNC`, set before `SDL_Init`). `SDL_UpdateTexture` in `main.c` is `mister_show()`: the 32-bit picture to the window's RGB565 surface, no renderer.
- Music: `fmchip.c` sends the register writes to the core's chip (`mister_fm_*`), `sound.c` says where in the audio block (`fmchip_at`). FM volume = 32 x 2.6 x the port's music level.
- Resolution is the OSD's: `O[25:24]` = 320x200 (default) / 320x240 / 640x200 / 640x240, for both games, followed at once wherever the program is (`tall_follow`, called with every event poll: the picture's memory always has the 40 extra rows, the window is resized, which sets the core's mode; a paused screen drawn from a kept copy -- the CD player, the question -- looks wrong until it is left). **There is no high resolution on the MiSTer** (Danik, 2026-10-12: the machine cannot fill 640x400; 2026-10-16 for Screamer 2 as well): `res_init` forces low, Screamer's OPTIONS page has no resolution line, Screamer 2's GAME SETTINGS neither (`S2_RES_ROW` in `s2r_car.h`). 320x240 (`g_tall` = 40 extra rows, `g_oy`, `LAY_TOP/MID/BOT`, `pic_put` in `main.c`; `OS_TALL=1` tries it anywhere, the PC build too): the 3D view has all 240 rows (eye line still 65% down, same lens, so more is seen above and below), and the game's 200-row artwork is never stretched -- whole-screen pictures, menus, the CD player, the question and the end-of-race words sit in the middle (20 black rows above and below a picture), the race's labels, clocks, countdown and start lights at the top, instruments, dashboard, radar and the replay's R at the bottom. Top and bottom things are where the HUD margins put them (`LAY_TOP` = *HUD (Top)*, `LAY_BOT` = 40 less *HUD (Bottom)*: 20 is the 200-row layout's own place; read every picture in `tall_follow()`, `mister_hud_margins()`; 10 without the core; it was a fixed 8 before host version 13). It costs about 1 ms a picture. The menu mask (`mister_menu_mask()`): bit 0 greys the HUD lines with 200 rows, bits 1 / 2 hide Screamer's / Screamer 2's cheats.
- Buttons: `J1` = Accelerate, Brake, Gear Up, Gear Down, View, Radar/Mirror, Back, Start, Menu OK, Menu Back; `mister_pad_mapping()` gives them SDL's controller names for `controls.c`. The library's Menu OK / Back (SDL buttons 28 / 29) are the "stick buttons" there, the core's own Menu OK / Back buttons (8 / 9, a spare button given them in *Define buttons*) MISC1 / PADDLE1 (before 2026-10-16 they were mapped to nothing). `controls_poll()` turns them into keys (START / BACK and the four menu buttons ENTER / ESC, the d-pad and the stick arrows in menus), and every key it sends down it also sends up: Screamer 2's menu keeps the keys held (`s2m_show()`), and without the releases an arrow stayed down for ever -- the gearbox jumped back to AUTOMATIC as the stick came back to the middle, and the menus took keys nobody pressed (Danik, 2026-10-17). Screamer 2's own joystick in its menu (`s2m_pad`) gives only left / right on the MiSTer: confirm and back are Menu OK / Menu Back (the rule in `hybrid/CLAUDE.md`); its accelerate / brake / shoulders were ENTER / ESC / down / up there, so gas confirmed and a Menu OK on the brake's button went back. The attract race is still ended by accelerate as well. A Screamer 2 race is not the loop's DRIVE mode, and until 2026-10-17 the controller was in menu mode through all of it (`controls_menu_mode()` in the race loop): X / Y did nothing and Menu Back (on Circle, which is also A) opened the pause screen. Now it is the car's while the race runs (not the attract race, the pause screen, a replay or after the finish). Checked on the MiSTer with a virtual pad and `screenshot` to `/dev/MiSTer_cmd`: X the mirror, Y the next view. **START pauses a race and resumes it, in both games** (Danik, 2026-10-17): in a race and on its pause screen START is the key PAUSE (`controls_start_back()`, set in the race loop; ENTER everywhere else): Screamer 2's pause screen, Screamer 1's CD player (its P, over the still race), and out of either again wherever the cursor is. SELECT does not pause: nothing in a Screamer 2 race, the leave question in Screamer 1's. Checked on the MiSTer the same way: Screamer 2 paused, the cursor moved to CD PLAYER, START back in the race; Screamer 1's CD player and back. Tests: `OS_S2MPAD="<picture>:<bits>,..."` (the six controls from that picture of the menu on), `OS_S2MLOG` prints the controls, the key the menu took and the gearbox page's state; `controls_poll` alone: a small program that pushes SDL events (stick across, d-pad, Menu OK, a button held from the menu into the race).
- `OS_FPSLOG=1` (set in the launch script for now): every ten seconds the log has the pictures a second and the milliseconds a picture took to make.
- Test on the PC: `./build.sh host`, `build/host/fakecore shm script audio.raw &`, then `MISTER_HYBRID_SHM=$PWD/shm OPENSCREAMER_HOME=<scratch> build/host/openscreamer -data ~/openscreamer/screamer`.

### State, 2026-10-12

Runs on the MiSTer at 320x200: intro, menus, race, backdrop, music on the chip. Speed with the robot at HI detail (ms a picture; a field is 16.7 and a picture is in time when it takes under about 15.2): track 1 15.5 in the first ten seconds, then 12.4 to 14.0; track 4 16.7, then 12 to 14.4; track 5 17.4, then 14 to 16.4. So: 60 a second everywhere but the first seconds of a race (the grid, ten cars) and one stretch of track 5, where it is 52 to 58. It began at 26 to 33 ms.

What it took, all on the game's branch `mister` (`git log`), checked against the PC's pictures with `build/test/cmp.py` and against one thread:
- the ground search by cell; the rasteriser with nothing divided or tested per row, 8-pixel texture spans, a lean loop for plain pixels, no maths-library calls (`floorf`, `fminf`: the ARM has no instruction for them);
- pieces, cars and props: a face turned away dropped first, a corner placed and projected once, faces off the picture or covering no pixel dropped before they are listed;
- the scene's triangles LISTED and filled by two threads in four lanes (every fourth row each; `lane_work`): the helper on CPU1 starts while the main thread still works the scene out, and paints the backdrop and clears the depths first;
- the backdrop in whole-number steps (it was 15 ms a picture); overlay pictures from runs; NEON to the screen; the audio device opened at 44100 (SDL's resampling took an eighth of CPU1);
- how far is drawn follows the time there is (`render_frame`: the far plane between the DETAIL setting and the game's own MID; `OS_FIXEDFAR=1` switches that off);
- `-O3 -marm -ffast-math` for the ARM build (the robot's telemetry is the same as the PC's to the last digit shown).
Tried and no use (do not try again without a new reason): the perspective division per pixel is not the cost; texture cache misses, the per-pixel buffers and prefetching them; writing colours at the end of the scene; sharing a triangle's set-up between lanes; eight lanes (a triangle's early tests times eight); the environment lookups.
What a picture's time is made of now (grid, track 1): the game 1.5 ms, the scene worked out 6.6 (the ten cars are a third of it), filling 6 after that with both threads busy, HUD 1.4, to the screen 0.7. CPU1 also carries the audio thread (6 %) and the copy of each picture to the core (10 %). The processor does about half an instruction a cycle on this code: everything costs twice what it looks.
Ideas left: hand the finished picture to the helper for the conversion and the copy (about 1 ms of the main thread); an 8-bit picture all the way (the core has a palette: half the copying, no conversion, the original's own way -- a rewrite of everything that draws).

### Screamer 2 on the MiSTer (host version 13, 2026-10-16)

- Built for the ARM as it is on the PC: the hand-written routines (`s2r_car.h`, `s2_hooks.c`; never `s2_gen.inc`, which is not in the repository). `S2_CONVERTED` is given to the target that compiles (`OS_COMPILED`: `os_objects` here); `s2_hooks.c` without `-ffast-math` (`-fno-fast-math`), so that the game's sums are done as written (`long double` is `double` on the ARM: the x87's 53 bits). Its statics are in `osbss` like the rest (23 MB all told).
- **Speed** (`OS_FPSLOG`, the attract race of the menu, robot cars, pictures a second): 320x200 57 to 59, 320x240 55 to 59, 640x200 37 to 44, 640x240 34 to 41; with Lock to 30 FPS 29.5 to 29.8. As Screamer, nothing done for Screamer 2's speed yet.
- **640 wide** (`g_s = 2`, `g_yd = 2`): `s2_screen_hi()` means "the H set and STARTH's places" (`g_s == 2`), at 640x400 on the PC and in both wide sizes; where a row of the screen counts (`s2m_picture`, `s2m_dark`, the clips, the view's and the mirror's rows, the menu's eye line) it is worked out from `g_yd`. The race's tracks stay the detail's set, as on the PC. `res_init` checks the H set's GAME1 / GRAF1 files.
- **240 rows**: the race as Screamer's (the view all rows, the HUD by the margins; view 6's dashboard is put down by the bottom margin and the scene goes on behind and under it, the eye line from the rows above it); the end's screen, the attract race's title cards and credits and the port's plain screens in the middle, the replay's band at the bottom, the mirror with the top's things. The game's own menu is drawn in 200 rows as it is and shown in the middle (`g_s2m_band` black rows above and below, `s2m_show()`; `tall_follow()` only changes the band there, a change of width starts the menu again).
- **Analog**: with a game controller there (`controls_pad()`), `s2_race_start()` makes the steering control the game's own joystick (the steering control's kind, `KEYS + 0x40`, 0: one word through its curve in `0x19409`), for the whole race (a replay keeps the record as it started); `s2_controls_pad()` gives the stick's word and the triggers' share of 1023 (`0x174ca` and `0x1756f` take any). The stick's word is + to the RIGHT (the joystick's: `0x19409`'s curve has the opposite sign to the keys'); it was the other way round at first and Danik found left and right swapped on the MiSTer (2026-10-16). Keys alone keep the key kind (full lock, eased). Test the real race loop with `OS_PADTEST="<stick>,<right trigger>,<left trigger>"` (SDL's numbers) and `OS_PADTEST6=1:0` (a controller there), `OS_S2LOG=1` for the cars' places, `OS_SHOTAT` to end it: on track 1 from the grid, stick left (-32767) takes the car to larger x, as the Left key. The headless run (`OS_S2RUN` with `OS_S2PAD`) did not show the stick reliably (whether its first frames take it depends on the time the run takes): do not judge the stick by it. The fakecore's `joy` / `analog` did not reach the game's controller in the host build either.
- **Rumble**: the PC's (`s2_rumble_step`, knocks, grass, skids) through the core's Rumble option, as Screamer's.
- **Cheats**: the OSD's triggers do what the typed words do, from the menu's frame (`s2m_osd_cheats()` in `s2_menu_hooks.h`, with the game's own word table at 0x113020): T[56] MRTRK, T[57] TACAR TBCAR TCCAR TDCAR, T[58] CHMPA. Screamer's: `cheats_follow()` every picture of a race (the switches turn over what the typed words left; not in the intro or a replay), the menu's loop for T[56] TAZOR, T[57] INVER and Afterburner Difficulty. - **Screamer 2's speed at 320x240, measured 2026-10-16** (robot, `OS_FPSLOG`; `/tmp/openscreamer_env` with `OS_TALL=1 OS_S2ROBOT=1000000 OS_LAPS=99` and `OS_DEV_ARGS="build/dec/MAPn n"`): tracks 1, 2, 6 53 to 59 a second, 3 40 to 59, 5 44 to 56, 7 44 to 55, 4 the worst, 43 to 51 (20 to 22 ms a picture: the scene listed 8.6, its filling after that 10.3; the helper fills 15 ms a picture and clears and paints the backdrop 2.2 to 3.3). On that picture (one pass of switches, since taken out): the triangles' set-up is about 3 ms of the helper, the rows 3.4, the pixels about 9; without any filling the listing takes 7.8 ms instead of 10.3 (the two processors share the memory: it is the limit); without the texture reads 1 ms less; rows in bands (each lane a band of the picture instead of every fourth row), eight lanes, the helper spinning instead of waiting for more triangles, `memset` for the clearing: no better. About 67,000 pixels are tested a picture (the screen has 76,800): little overdraw. - **Development tools**: `OS_PROF=<seconds>` in the game's environment: a sampling profile of the program's time (both threads; SDL's threads have SIGPROF unblocked in `mister_second_cpu()`), written to `/tmp/openscreamer_prof.txt` ("address count thread") and `/tmp/openscreamer_prof_maps.txt`; resolve the addresses with `arm-linux-gnueabihf-addr2line -a -f -i -e build/mister/openscreamer` (a `./build.sh mister RelWithDebInfo` build has the lines; still -O3).
